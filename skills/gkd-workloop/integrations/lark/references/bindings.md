# 将飞书问题表关联到本地项目

在以下情况使用：创建表成功后、处理已有表且需要定位代码项目时、用户要求查看/修改/移除绑定时。由**当前主 Agent** 判断项目归属；`scripts/bindings.ts` 只负责本地存储，不访问飞书、不修改业务代码，也不证明推断正确。

## 绑定记录

存储文件：`${PI_CODING_AGENT_DIR:-~/.pi/agent}/lark-workloop/workspace-bindings.json`。首次核实保存时创建；不存在时读取空结果且不生成文件。`check-lark --invalidate` 不会清除此文件。

| 字段                  | 用途                                                 |
| --------------------- | ---------------------------------------------------- |
| `baseToken + tableId` | 真实 Base 和表 ID，共同确定问题表                    |
| `workspace`           | 当前会话允许使用的绝对真实工作区目录                 |
| `project`             | 工作区内相对项目路径；单项目可为 `.`                 |
| `source`              | `user`（用户指定/确认）或 `inferred`（代码证据推断） |
| `evidence`            | 简短的归属依据                                       |
| `id`                  | 单条绑定的稳定标识，用于更新或移除                   |

每条记录还包含更新时间。**视图不参与长期绑定键**：它只限制本轮扫描范围。Wiki token 不是 Base token；必须解析真实 Base、表和视图，同表允许绑定多个工作区或子项目，不能用新关联覆盖其他项目。

## 1. 确认表和工作区

1. **新建表**：只在 `create.ts` 退出码为 `0` 且 `status=created` 时，直接使用返回的 `baseToken`、`tableId`。不再解析链接或读取示例记录。创建状态不明时先核对，不重跑创建。
2. **已有表**：通过官方 CLI 解析到真实 Base 和表，不能用 Wiki token 代替。
3. **选择工作区**：本轮显式 `--workspace` 优先，否则用当前 Agent 会话 `cwd`（Pi 快捷入口携带的 cwd 优先），不是 Skill 目录或上次 shell `cd` 的目录。
4. 将工作区和子项目解析为真实路径。只允许当前会话 cwd 及其子目录；外部目录、父级仓库根或符号链接越界时，请用户在目标目录重新打开会话。
5. 用户说明“仅本次使用”或“不要保存”时只用本次目录，不持久化。

## 2. 读取已有绑定

使用 Node.js >= 22.19.0；`<lark-dir>` 指 Skill 内 `integrations/lark` 的绝对路径。通过 stdin 传 JSON：

```bash
node --experimental-strip-types "<lark-dir>/scripts/bindings.ts" <<'JSON'
{"action":"read"}
JSON
```

成功结果包含 `status: "ready"`、`version: 1`、`bindings` 和 `revision`。不要直接编辑 JSON 文件。

复用记录前逐条检查：

- 目录确实存在、路径在当前工作区边界内，且能对应**本条问题**。
- 多个子项目匹配时结合问题、调用链和代码选择；不默认取第一项。
- 旧绑定指向另一个工作区时，不静默切换或改绑。询问是临时在当前目录执行、切回原工作区，还是永久更换绑定。
- 已失效、权限冲突或归属不明时重新核对，不创建缺失目录，也不把旧路径当授权。当前 cwd 位于旧子项目中时可用其线索，但不得扩大修改边界。

## 3. 推断项目归属

1. 只读当前范围内的 `AGENTS.md`、`README`、workspace/package 配置及相关代码，结合问题描述、调用关系和实际行为定位子项目。
2. 单项目可用 `project: "."`；monorepo 要记录实际子项目（如 `apps/web`），不能因为 cwd 在仓库根就自动绑定 `.`。新建表的示例记录不是归属证据。
3. 证据充分且没有冲突时自动保存，无需逐次询问。保存可发生在创建后、问题定位或修复阶段，新的可靠证据出现后可更新。
4. 证据不足、多个候选或冲突时，询问用户具体项目；确认前不改该问题代码、不写入推断结果。用户明确指定或确认的记录标记 `source: "user"`；自动推断为 `"inferred"`。

旧的 `source: "user"` 不得被新推断降级。发现新项目时新增独立关联；只有明确迁移证据排除旧归属，或用户明确要求更换时，才更新原记录。单纯显式目录不等于永久改绑。

## 4. 保存或修改绑定

**每次写入前必须 read，并使用该次返回的 `revision`**。向相同脚本的 stdin 发送：

```json
{
  "action": "save",
  "expectedRevision": "<本次 read 返回的 revision>",
  "binding": {
    "baseToken": "<真实 Base token>",
    "tableId": "<真实 table_id>",
    "workspace": "/absolute/repository",
    "project": "apps/web",
    "source": "inferred",
    "evidence": "apps/web/package.json 与实际代码确认问题归属"
  }
}
```

- **新增**：省略 `id`。同表、同工作区和同项目的记录会更新，不重复新增；其他项目保留。
- **修改**：提供目标绑定的原 `id`，只更新这一条；不能拿此 ID 指向另一张表。
- **人工优先**：禁止以 `inferred` 覆盖 `user`；要更换人工确认的归属，先取得用户明确确认，再以 `user` 更新。
- **路径限制**：`workspace` 必须是存在的绝对目录，`project` 是内部相对路径，默认 `.`；脚本拒绝 `..`、绝对项目路径、文件和符号链接越界。
- **成功**：收到 `status: "saved"` 后记录最新 revision，简短反馈“已记录/更新绑定：表 → 工作区 → 子项目”。

## 5. 移除绑定

用户明确指出要删除的关联后，先 read，再发送：

```json
{ "action": "remove", "id": "<明确选中的关联 id>", "expectedRevision": "<本次 revision>" }
```

只删除目标 `id`，保留同表其他关联。已失效的旧目录也可以明确移除，无需访问旧目录；成功状态为 `removed`。仅要求查看或预览时只 read，不保存也不删除。

## 6. 处理写入冲突和中断

- 脚本以 `expectedRevision`、排他锁、同目录临时文件和 rename 保护写入，文件权限为 `0600`。每次保存/移除后，下一次写入都使用**最新** revision。
- 版本冲突时重新 read 并重新判断归属，不能只替换 revision 后盲目重试。
- `status: "error"`、进程非零退出、文件损坏或未知结果：保留原文件，核对真实内容和目标状态；不清空、覆盖或宣称成功。
- 遗留 `workspace-bindings.json.lock` 时，先确认没有活动写入，再请用户处理；不要自行删锁或与外部编辑器并发改文件。
- **创建成功、绑定失败**：保留已建表及链接，说明“表已创建，绑定未完成”；不重新创建。
- **开发中绑定失败**：未修改代码则暂停；已有改动则保留并报告，不重做修复以重试保存。

本地绑定是项目定位记录，不是任务锁、代码执行授权或验收依据。不存凭据、令牌、授权链接、完整问题正文或日志；`evidence` 只写必要路径与核实结论。
